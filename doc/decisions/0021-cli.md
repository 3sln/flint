# 0021 — A native CLI: cross compiler, interpreter, and capabilities

> **PARTLY BUILT.** `flint build` / `run` / `tasks` / `task` / `deps` / `fetch` /
> `paths` / `targets` all work, with git, npm and maven dependencies at exact
> versions. Still to do: the native binary itself, cross-compilation backends
> (`0010`), nREPL, and capability injection on the command line. Maven's
> transitive resolution is **cancelled** — see the measurement below.

The ask, in the user's terms:

- A **per-platform CLI**, produced by CI per release with **wasmer**, installed
  from a script on the deck's intro card.
- It carries **the compiler and an interpreter**.
- It **cross compiles**: emit artifacts for any supported runtime — wasm now,
  **JVM and CLR later** (`0010`).
- Later, **nREPL** and **capability injection**:
  `flint run :with [:http :fs] :src "..." :fn my-namespace/my-fn`, with the
  capabilities arriving as a second argument to the entry function:
  `(the-fn argv {:http <token> :fs <token>})`, the token being a string that can
  be opened.
- **`deps.edn`** support for the parts that integrate easily: **git/gh, npm and
  maven** deps — npm and maven both because a jar and a tarball can each carry
  `.cljc`.
- **`:flint/tasks`** in `deps.edn`, in the shape of babashka's tasks.
- The goal named for all of it: *"neat for general project scripting."*

## The thing this removes, which is the strongest argument for it

`bin/flint` is a **babashka script**. flint bootstraps on babashka and always
has (`0003`), which is fine for developing flint and is a wall for everyone
else: the npm package published in `0.1.0` ships a shim whose entire job is to
say *install babashka first*.

A native CLI removes that. flint self-hosts — byte-identical fixpoint, asserted
by `test/selfhost.clj` — so **the compiler is a flint program**, and a flint
program compiles to wasm, and a wasm module becomes a native executable. The
dependency chain ends: one binary, nothing installed underneath it.

That is the reason to build this, more than the scripting convenience. Today
flint is a thing you can use if you already have a Clojure toolchain. A binary
makes it a thing you can use.

## How it is built

**`wasmer create-exe`** turns a `.wasm` into a native executable, which is the
mechanism the user named and the shortest path.

**The alternative worth pricing before committing**: a small Rust host that
embeds a wasm engine and the module via `include_bytes!`. More work up front,
but it controls its own argument parsing, exit codes, stdio and signal handling
rather than inheriting whatever the exe generator provides, and it removes a
build-time dependency on one vendor's tool. If `create-exe` fights the release
matrix, this is the fallback rather than a redesign.

**The matrix is the real cost.** Native binaries per platform means runners per
platform: `ubuntu-latest` (x64, and aarch64 via cross), `macos-latest` (arm64)
and `macos-13` (x64), `windows-latest`. Four to five assets per release, each
with a checksum, published as release assets by a workflow that runs on
`release: published` alongside `publish.yml`.

**Two notes so nobody rediscovers them:**

- **Gatekeeper does not block a `curl`ed binary.** Quarantine is set by browsers,
  not by curl, so a `curl … | sh` install works unsigned. A binary a user
  *downloads in a browser* does get blocked, which is an argument for the script
  being the documented path and signing being a later nicety.
- **The compiler needs the filesystem**, so the CLI's own host half grants itself
  `:fs` unconditionally. That is the same mechanism as user capabilities, at a
  different trust level — see below.

## Cross compilation

`flint build :target wasm` today; `:jvm` and `:clr` when `0010` lands.

The CLI is the natural front end for this, and there is a pleasing consequence
of it being a flint program compiled to native: **emitting for a target has
nothing to do with running on it.** A macOS CLI emits JVM bytecode without a JVM
present, because emission is codegen and codegen is pure. The targets differ in
their backends, not in the toolchain around them.

`0010` should be read as the backend work and this document as the front end.

## Capabilities, which turn out to be nearly free

**The mechanism already exists.** `0005` and `0006` give flint ports as
capabilities: `(p/open "the-thing" {:codec edn/codec})` raises an `open-request`
event carrying a token, a port id and **the capability name**; the host either
lends the port or answers `:refused`. The README already says the consequence
out loud — *a host that grants nothing runs a pure program*.

So the user's design maps onto it exactly, with **no VM change at all**:

- `:with [:http :fs]` is an **allow-list on the CLI's host half**. Names on the
  list get a port; everything else is refused, which is the existing refusal
  path rather than a new one.
- The map handed to the entry function, `{:http "…" :fs "…"}`, carries the
  **names to open**. `(p/open (:fs caps))` yields the port.
- Ports are not transferable (`0005`), so a granted capability cannot leak
  through a message. That property is already built and already tested.

### A capability is a first-class object, and identity is the authority

> Generalised in **`0022`**: the primitive is an *opaque value*, and a capability
> is a host-minted one. The reasoning below stands; the type is not
> capability-specific. Note the hazard `0022` records — because guest code can
> mint opaque values of its own, a capability check must test the host's grant
> table and never the type.

**Decided, and it supersedes the secret-token design that stood here.** Making
the token a cryptographic secret worked, but it bought unforgeability with
crypto and then had to defend that crypto — constant-time comparison, host
entropy, tokens recorded for replay, secrets sitting in exported snapshots. Four
obligations, all of them consequences of the choice rather than of the problem.

**A built-in capability removes the class.** A capability is a heap object of its
own type. `open` takes the name of the thing wanted and, as its second argument,
the capabilities the caller holds:

```clojure
(p/open "/etc/hosts" [fs-cap] {:codec edn/codec})
```

Possession *is* the authority. There is no secret, so there is nothing to
compare in constant time, nothing to seed from entropy, nothing to record for a
replay, and nothing sensitive in a snapshot.

**What makes it unforgeable is the value encoding, not a secret.** A capability
is a heap reference, and guest code cannot fabricate one: flint has no operation
that turns a fixnum into a heap pointer, and the NaN-boxed tag is not something
a program can set. Only the host mints capabilities. That is a stronger
guarantee than an unguessable string — an unguessable string can in principle be
guessed, and this cannot be constructed at all.

**And it keeps every property the secret was bought for.** A stranger calling
`(p/open "/etc/hosts" [])` fails, because it holds no capability to pass.
Propagation stays explicit, because the capability is a value the caller must
hand over. Attenuation stays available, because the entry function chooses what
goes into each callee's list.

**Why the name survives alongside the capability.** A capability is a *class* of
authority rather than a single resource — `:fs`, not `/etc/hosts`; `:http`, not
one URL. So the caller still names what it wants and presents the authority
under which it may. One capability, many opens, which is also why the capability
and the port stay distinct objects: the capability is standing authority, the
port is one connection.

This also opens a door the string design closed: **derived capabilities**. A
capability object can later be narrowed — `:fs` restricted to a subtree, `:http`
to one origin — by the host minting a child. That is natural for an object and
awkward for a name.

**The comparison is identity over a short list**, which is O(n) in a list of one
or two, with no timing concern: the failure mode is "you do not hold it", which
the caller already knows. Contrast the secret design, where `0009`'s
deterministic and observable instruction count made a byte-at-a-time compare a
precise oracle — the reason that design needed defending.

**Revocation becomes easy**, too: the host marks a capability spent or invalid
and subsequent opens refuse, with no key rotation and no cache to clear.

### One thing this design does need to answer: snapshot import

`0015` exports a snapshot and imports it again. A capability is an ordinary heap
object, so a naive import would **resurrect live authority** — a snapshot taken
from a run granted `:fs` would carry `:fs` into whatever imports it.

So on import, capability objects are re-bound by the host or invalidated; they
are never restored as authority. This is the mirror of the concern the secret
design had on *export*, and it is the smaller one: export leaked a secret to
anyone reading the file, whereas import only matters if the importing host
chooses to honour it.

### What this does and does not guarantee

Worth stating so the mechanism is not over-trusted. The runtime guarantees
**unforgeability**: code that was never given a capability cannot construct one,
and cannot receive one through a port, because ports are not transferable
(`0005`). With an object rather than a secret there is no third case — nothing
to guess.

It does not guarantee **containment**. A library handed a capability is holding
a value, and a value can be stashed in a dynamic var, closed over, or written
into a structure that something else reads. flint has dynamic vars, so a caller
*can* make a capability ambient by binding one — the runtime will not stop it.

So the property is: *you cannot reach a capability you were never given.* Not:
*capabilities cannot spread.* The first is enforced; the second is discipline,
and the CLI's job is to make the discipline the path of least resistance by
handing the entry function a plain map and nothing else.

## `deps.edn`, and an honest note about what it buys

Three sources, and their costs are not close to equal:

- **git / `io.github.…`** — clone at a sha, add its paths. Cheap, and it is
  where a flint-specific library ecosystem would actually live.
- **npm** — registry metadata, fetch a tarball, take the `.cljc` in it. Moderate.
  Reasonable because the cherry/squint world already ships `cljc` this way.
- **maven** — POM parsing, the transitive graph, version conflict resolution.
  **Much** more expensive than the other two, and the piece most likely to be
  half-built.

**And the caution that matters more than the cost.** Resolving a maven
coordinate gets you *source*; it does not get you something that compiles.
`0012`'s and the README's divergence lists are the reason: most Clojars
libraries reach for host interop, `deftype` on host classes, `java.io`,
reflection, or `core.async`. flint has none of that. The subset that works is
**pure portable `cljc` with no interop** — real, and much smaller than the
registry suggests.

So the value is genuine but should be stated as: *use a library written to be
portable*. Building maven resolution and then discovering that four fifths of
Clojars will not compile would be the expensive way to learn it. **Suggest git
first, npm second, maven last** — in the order of cost, which happens also to be
the order of how likely the fetched code is to actually build.

### Measured, and the expensive half is not worth building

**Built:** git, npm and maven all fetch one coordinate at one exact version. An
exact coordinate is a derived URL for all three, so that half cost almost
nothing. **Not built, and now deliberately not:** POM parsing, the transitive
graph, version conflict resolution.

The survey that decided it — 135 `.cljc` namespaces sampled from 20 well-known
Clojure libraries, biased *towards* ones that ship `cljc`, so this is the best
case rather than the registry mean:

| features | clean | cut | unreadable | missing require | other error |
|---|---:|---:|---:|---:|---:|
| `#{:flint}` | 11 | 17 | 20 | 35 | 52 |
| `#{:flint :cljs}` | 12 | 6 | 5 | 83 | 29 |
| `#{:flint :clj}` | 12 | 6 | 10 | 65 | 42 |

**8.9% compile cleanly.** *Clean* means compiled with nothing silently deleted
— the distinction that matters, because a reader conditional matching nothing
deletes the form it stood in, so 17 of the 28 that "compiled" under `#{:flint}`
were mutilated. Before that was counted the figure looked like 20.7%.

**And the 83 missing requires decompose in a way that settles the question:**

| what is missing | count | would transitive resolution fix it? |
|---|---:|---|
| `goog.*`, `cljs.*` — ClojureScript runtime | 35 | **No.** flint will never have these. |
| `clojure.*` flint lacks (`spec.alpha`, `zip`, `data`, `datafy`, `tools.reader`) | 24 | **No** — but *implementing them* would. |
| another artifact | 24 | **Yes.** |

So transitive resolution is worth at most 24 of 135, and only where those
artifacts themselves compile — at 8.9%, that is about two namespaces. Whereas
`clojure.zip`, `clojure.data` and `clojure.datafy` are pure Clojure that flint
could simply implement, and they block more.

**The conclusion is therefore the opposite of a roadmap item: maven's expensive
half is cancelled, and the effort it would have taken belongs in the core
library instead.** Revisit only if the clean-compile rate rises far enough that
missing artifacts become the binding constraint.

**What the survey found in flint rather than in the registry** — worth recording
because it was the majority of the failures, and because none of it was visible
before the survey ran:

- `#?@` never spliced, in any collection. Conditionally adding a `:require` is
  the common way to write portable `cljc`.
- The splice marker was a map that flint's own reader contains as a literal.
- A conditional matching nothing deleted forms silently; the reader now reports
  every one, with file, line and the branches offered.
- `:features` was threaded to the compiler but not to the two reads in
  `bin/flint` that decide what gets compiled, so the knob did nothing.
- `(defn f #?(:clj [x]) ...)` crashed with a host exception rather than saying
  the argument vector was missing.

## `:flint/tasks`

A submap in `deps.edn`, in babashka's shape. This is the smallest piece here and
the one most directly serving *"neat for general project scripting"*, so it
should not wait for maven resolution to be finished. It needs the CLI, dependency
paths, and nothing else.

## nREPL

Listed by the user as later, and it is: it wants the CLI, and it overlaps
heavily with `0014`'s debug runner, which already proposes nREPL and DAP on the
grounds that *a breakpoint is a park*. **These should be one implementation**,
not two — `0014` and this section describe the same server from two directions.

## The install card

**Not written yet, deliberately.** The deck's intro card gets the install script
when the first release actually produces binaries; documenting a `curl` command
that 404s is worse than documenting nothing. What lands there is a `uname`-based
shell one-liner and a PowerShell equivalent, both resolving the latest release
asset for the detected platform and verifying its checksum.

## What must be true before this is called done

- **`flint` runs with nothing else installed** — no babashka, no JVM, no node.
  A test on a clean runner asserts it, because that is the entire point.
- **The self-hosting fixpoint still holds** through the native CLI: the binary
  compiles flint and gets the same bytes (`test/selfhost.clj`).
- **A program not granted a capability cannot open it**, and a program *granted*
  one cannot open it from a subroutine that was never handed the token. Both
  asserted, not argued.
- **Guest code cannot fabricate a capability.** Asserted directly: no fixnum,
  string, or constructed value passes as one, and no arithmetic produces one.
- **An imported snapshot grants nothing** — `0015` round-trips a run that held
  `:fs`, and the imported copy cannot open it.
- **Capabilities cost no determinism.** A run with capabilities is still
  bit-reproducible, because nothing random entered it.
- **The npm package and the binary agree** on version and behaviour, or the npm
  package becomes a downloader for the binary rather than a second
  implementation.
- Every dependency source states what it does **not** support, in the manifest
  style the README already uses for library coverage.
