# 0021 — A native CLI: cross compiler, interpreter, and capabilities

> **NOT BUILT YET.** Scheduled after AOT (`0013`) and the string/rope/regex work
> (`0011`, `0012`), per the user's own ordering.

The ask, in the user's terms:

- A **per-platform CLI**, produced by CI per release with **wasmer**, installed
  from a script on the deck's intro card.
- It carries **the compiler and an interpreter**.
- It **cross compiles**: emit artifacts for any supported runtime — wasm now,
  **JVM and CLR later** (`0010`).
- Later, **nREPL** and **capability injection**:
  `flint run :with [:http :fs] :src "..." :fn my-namespace/my-fn`, with the
  capabilities arriving as a second argument to the entry function:
  `(the-fn argv {:http <token> :fs <token>})`, the token being a string that can
  be opened.
- **`deps.edn`** support for the parts that integrate easily: **git/gh, npm and
  maven** deps — npm and maven both because a jar and a tarball can each carry
  `.cljc`.
- **`:flint/tasks`** in `deps.edn`, in the shape of babashka's tasks.
- The goal named for all of it: *"neat for general project scripting."*

## The thing this removes, which is the strongest argument for it

`bin/flint` is a **babashka script**. flint bootstraps on babashka and always
has (`0003`), which is fine for developing flint and is a wall for everyone
else: the npm package published in `0.1.0` ships a shim whose entire job is to
say *install babashka first*.

A native CLI removes that. flint self-hosts — byte-identical fixpoint, asserted
by `test/selfhost.clj` — so **the compiler is a flint program**, and a flint
program compiles to wasm, and a wasm module becomes a native executable. The
dependency chain ends: one binary, nothing installed underneath it.

That is the reason to build this, more than the scripting convenience. Today
flint is a thing you can use if you already have a Clojure toolchain. A binary
makes it a thing you can use.

## How it is built

**`wasmer create-exe`** turns a `.wasm` into a native executable, which is the
mechanism the user named and the shortest path.

**The alternative worth pricing before committing**: a small Rust host that
embeds a wasm engine and the module via `include_bytes!`. More work up front,
but it controls its own argument parsing, exit codes, stdio and signal handling
rather than inheriting whatever the exe generator provides, and it removes a
build-time dependency on one vendor's tool. If `create-exe` fights the release
matrix, this is the fallback rather than a redesign.

**The matrix is the real cost.** Native binaries per platform means runners per
platform: `ubuntu-latest` (x64, and aarch64 via cross), `macos-latest` (arm64)
and `macos-13` (x64), `windows-latest`. Four to five assets per release, each
with a checksum, published as release assets by a workflow that runs on
`release: published` alongside `publish.yml`.

**Two notes so nobody rediscovers them:**

- **Gatekeeper does not block a `curl`ed binary.** Quarantine is set by browsers,
  not by curl, so a `curl … | sh` install works unsigned. A binary a user
  *downloads in a browser* does get blocked, which is an argument for the script
  being the documented path and signing being a later nicety.
- **The compiler needs the filesystem**, so the CLI's own host half grants itself
  `:fs` unconditionally. That is the same mechanism as user capabilities, at a
  different trust level — see below.

## Cross compilation

`flint build :target wasm` today; `:jvm` and `:clr` when `0010` lands.

The CLI is the natural front end for this, and there is a pleasing consequence
of it being a flint program compiled to native: **emitting for a target has
nothing to do with running on it.** A macOS CLI emits JVM bytecode without a JVM
present, because emission is codegen and codegen is pure. The targets differ in
their backends, not in the toolchain around them.

`0010` should be read as the backend work and this document as the front end.

## Capabilities, which turn out to be nearly free

**The mechanism already exists.** `0005` and `0006` give flint ports as
capabilities: `(p/open "the-thing" {:codec edn/codec})` raises an `open-request`
event carrying a token, a port id and **the capability name**; the host either
lends the port or answers `:refused`. The README already says the consequence
out loud — *a host that grants nothing runs a pure program*.

So the user's design maps onto it exactly, with **no VM change at all**:

- `:with [:http :fs]` is an **allow-list on the CLI's host half**. Names on the
  list get a port; everything else is refused, which is the existing refusal
  path rather than a new one.
- The map handed to the entry function, `{:http "…" :fs "…"}`, carries the
  **names to open**. `(p/open (:fs caps))` yields the port.
- Ports are not transferable (`0005`), so a granted capability cannot leak
  through a message. That property is already built and already tested.

### The token is a cryptographic secret, and propagation is explicit

**Decided.** The token is an unguessable secret minted per run, not the
capability's name. A plain name would mean any code in the program could call
`(p/open "fs")` whether or not the entry function passed it down — authority
would be per-run, and every library the program loads would hold everything the
program holds. That is ambient authority with extra steps.

With a secret, `(p/open "fs")` by a stranger fails, and the entry function
decides what to hand to whom. **Capabilities propagate explicitly, as values, or
they do not propagate.**

The host ABI does not change: `open-request` already carries "the capability
name" (`0006`), and the token simply *is* that field. The host looks the token
up in a table it minted; an unknown token takes the existing `:refused` path.
Keep the token opaque rather than structured as `fs:<secret>` — a structured
token invites parsing, and parsing invites accepting the prefix.

Four requirements that follow, none of them obvious:

**Compare in constant time.** This matters more here than in an ordinary system.
A naive byte-at-a-time comparison with an early exit is a timing oracle, and
guest code in this VM has a *far* better clock than wall time: `0009` makes the
instruction count deterministic and observable, so a guess that matches one more
byte costs measurably more. That turns an unguessable secret into a few thousand
guesses. Constant-time comparison is not a hardening nicety here, it is what
makes the secret a secret.

**Mint from real entropy, on the host side.** flint's module imports nothing and
its VM is deterministic by construction, so it has no entropy of its own and
should not grow any. The CLI's native half mints the token — 256 bits, hex or
base64url — and hands it in. That keeps the randomness outside the deterministic
core, which is where it belongs.

**A run with capabilities is no longer bit-reproducible unless the tokens are
replayed.** `0005` and `0009` buy determinism, and `0015`'s snapshot plus the
host event log is meant to be a complete replay. A fresh random token per run
breaks that the moment a program branches on the token's bytes — or merely
prints it. So the minted tokens are part of the recorded run state, and a replay
re-injects them rather than minting new ones. Cheap if it is designed in; a
puzzle if it is discovered later, which is the reason it is written here.

**A snapshot contains live capability secrets.** Tokens are ordinary strings in
the heap, and `0015` exports snapshots to a file with an inspector that can read
them. An exported snapshot is therefore exactly as sensitive as the capabilities
the run held. Either redact tokens on export or say plainly that a snapshot is a
secret — but decide, rather than discovering it when one is attached to a bug
report.

### What this does and does not guarantee

Worth stating so the mechanism is not over-trusted. The runtime guarantees
**unforgeability**: code that was never given a token cannot obtain one, cannot
guess one, and cannot receive one through a port, because ports are not
transferable (`0005`).

It does not guarantee **containment**. A library handed a token is holding a
value, and a value can be stashed in a dynamic var, closed over, or written into
a structure that something else reads. flint has dynamic vars, so a caller *can*
make a capability ambient by binding one — the runtime will not stop it.

So the property is: *you cannot reach a capability you were never given.* Not:
*capabilities cannot spread.* The first is enforced; the second is discipline,
and the CLI's job is to make the discipline the path of least resistance by
handing the entry function a plain map and nothing else.

## `deps.edn`, and an honest note about what it buys

Three sources, and their costs are not close to equal:

- **git / `io.github.…`** — clone at a sha, add its paths. Cheap, and it is
  where a flint-specific library ecosystem would actually live.
- **npm** — registry metadata, fetch a tarball, take the `.cljc` in it. Moderate.
  Reasonable because the cherry/squint world already ships `cljc` this way.
- **maven** — POM parsing, the transitive graph, version conflict resolution.
  **Much** more expensive than the other two, and the piece most likely to be
  half-built.

**And the caution that matters more than the cost.** Resolving a maven
coordinate gets you *source*; it does not get you something that compiles.
`0012`'s and the README's divergence lists are the reason: most Clojars
libraries reach for host interop, `deftype` on host classes, `java.io`,
reflection, or `core.async`. flint has none of that. The subset that works is
**pure portable `cljc` with no interop** — real, and much smaller than the
registry suggests.

So the value is genuine but should be stated as: *use a library written to be
portable*. Building maven resolution and then discovering that four fifths of
Clojars will not compile would be the expensive way to learn it. **Suggest git
first, npm second, maven last** — in the order of cost, which happens also to be
the order of how likely the fetched code is to actually build.

## `:flint/tasks`

A submap in `deps.edn`, in babashka's shape. This is the smallest piece here and
the one most directly serving *"neat for general project scripting"*, so it
should not wait for maven resolution to be finished. It needs the CLI, dependency
paths, and nothing else.

Listed by the user as later, and it is: it wants the CLI, and it overlaps
heavily with `0014`'s debug runner, which already proposes nREPL and DAP on the

## The install card

**Not written yet, deliberately.** The deck's intro card gets the install script
when the first release actually produces binaries; documenting a `curl` command

## What must be true before this is called done

- **`flint` runs with nothing else installed** — no babashka, no JVM, no node.
  A test on a clean runner asserts it, because that is the entire point.
- **The self-hosting fixpoint still holds** through the native CLI: the binary
  compiles flint and gets the same bytes (`test/selfhost.clj`).
- **A program not granted a capability cannot open it**, and a program *granted*
  one cannot open it from a subroutine that was never handed the token. Both
  asserted, not argued.
- **The token comparison is constant-time**, with a test that measures it in
  instructions rather than reasoning about the code — `0009` makes that exact.
- **A recorded run replays with its tokens**, so capabilities do not cost the
  determinism `0005`, `0009` and `0015` are built on.
- **The npm package and the binary agree** on version and behaviour, or the npm
  package becomes a downloader for the binary rather than a second
  implementation.
- Every dependency source states what it does **not** support, in the manifest
  style the README already uses for library coverage.
